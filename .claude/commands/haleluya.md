The user has invoked the finish-feature shorthand ("haleluya" or a spelling variant, or this `/haleluya` command). See `.github/METHODOLOGY.md`'s "Finish-Feature Trigger Phrase" section and `CLAUDE.md`'s Spec-Driven Workflow section for the authoritative definition.

This assumes the actual work (feature or bugfix) in the current branch is already done and approved by the user — do not use this to skip any gate (tests must already pass, CONSTITUTION checks already satisfied). If work looks incomplete or unapproved, stop and check with the user before proceeding.

**Haleluya never touches `dev`/`prod` in any way** (2026-08-07) — no test-deploy, no rebuild, no dev-lock release, no teardown. Which environment(s) run what, and when, is always a separate, explicit human decision made outside this flow — haleluya's job ends at "merged to master and docs are in order."

Do the following, in order:

1. **Verify a spec exists**: extract the numeric ID from the branch name (e.g. `024` from `feature/024-ledger-event-recognition`, `009` from `bugfix/009-...`) and confirm a matching spec file is actually committed to git under `specs/` (any of `backlog/`, `in-progress/`, `done/`, `obsolete/`, `bugfixes/`, `done/bugfixes/`, `obsolete/bugfixes/`, `not_reproducible/bugfixes/` — check both the working tree and `git log --all --oneline --name-only | grep <id>` in case it exists but isn't staged/committed yet on this branch). **If no spec is found, STOP here and tell the user before doing anything else** — do not commit, push, or merge. This exists because feature 024 (Ledger Event Recognition) was fully implemented and merged with **no spec file ever committed at all** (confirmed via full git history search, 2026-07-30) — silently proceeding past a missing spec is exactly how that happened, and haleluya assuming "the work is already done" must not extend to assuming its spec exists too.
2. **Review the diff**: `git status` / `git diff --stat` against the branch's base. Confirm nothing unexpected (secrets, stray files, runtime data) is staged.
3. **Docs update + spec cleanup — BEFORE committing, so it all ships in ONE PR (2026-08-07, no longer a separate follow-up PR)**: previously this repo did the docs/spec-move as a second PR after the feature PR merged (e.g. PR #198 feature, PR #199 separately titled "docs/...-spec-cleanup") — don't do that anymore; fold it into the same commit/PR as the feature work itself.
   - If the change affects `CLAUDE.md`, `README.md` files, or other docs and they weren't already updated as part of the feature work, update them now.
   - Move the feature/bugfix spec to its correct `specs/` folder per METHODOLOGY.md §XI's Folder Movement Rules (typically `specs/done/` for a merged feature), and update its `Status` line to reflect the merge. The exact PR number isn't known yet at this point — write the Status line without it for now (e.g. "Done - implemented and tested, merging to master"); step 6 below fills it in once the PR exists, still within this same PR/branch, never a separate one.
4. **Commit**: stage the relevant files, code and docs/spec-move together (never a blind `git add -A` without reviewing status first) and commit with a descriptive message following this repo's conventional-commit style (see recent `git log` for examples), ending with the `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>` trailer.
5. **Push**: push the current branch to `origin` with `-u` if not already tracking.
6. **Open a PR**: `gh pr create` with a concise title and a body covering Summary + Test plan, per this repo's PR conventions. Once it's created and you have the real PR number, go back and fill it into the spec's `Status` line from step 3 (e.g. "Done - Merged to master (PR #N)"), commit that small addendum (`docs(NNN): record PR #N in spec status line`), and push again — still the same branch/PR, so this stays a single PR, not two.
7. **Merge**: `gh pr merge --merge` (regular merge commit, never squash, per CONSTITUTION.md §III).
8. **Sync**: after confirming the merge succeeded, sync local `master` (`git checkout master && git pull`). **NEVER delete git branches** — not the just-merged branch, not any other branch, locally or remotely, `-d` or `-D`, as part of this flow or any other step above. Leave the merged branch in place; if the user wants it deleted, they'll say so explicitly.
9. **Release prompt**: for each app the finished work touched, ask the human whether to cut a release — never silently skip this, never decide the answer. If yes, ask for the **exact version string** and wait for it; never suggest, compute, or default one (CLAUDE.md's "VERSION AND RELEASE DECISIONS ARE HUMAN-ONLY" banner). Skipping the release for a given app is a valid answer, but the question itself is never skipped. Cutting a release (`scripts/cut_release.sh`) is separate from deploying it anywhere — this step only covers cutting, never deploying; deploying (to any environment, including `dev`) is always its own separate, explicit, freshly-approved request from the human, entirely outside this flow.
10. **Report**: a brief summary of what was merged (PR number/link) and whether a release was cut (and to what version(s)) per step 9.

If any step requires a permission this environment doesn't grant automatically (e.g. push blocked by a classifier), stop and ask the user rather than working around it.
