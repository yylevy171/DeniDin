# Flow: Deposit provided by the user

Goal: the user reported or forwarded money received - as text, or as a bank slip, a Bit or PayBox confirmation, or a photo of a cheque (or cash, reported in words). Make sure its client exists in Morning, and get a Morning document for it only when the user asks for one.

Capabilities: `cap_media_analysis`, `cap_client_read`, `cap_approval_with_buttons`, `cap_ledger_query`, `cap_ledger_capture`.
Flows it may load: `flow_add_client`, `flow_morning_document_write`.

Follow these steps in order, to the letter.

🚨 **Dropping out applies at every step, not as a step of its own:** if at any point the user drops the request or changes the subject, do nothing further and treat the flow as complete. Anything already recorded stays recorded.

🚨 **When the deposit came with a slip, the deposit's date is ALWAYS the date on the slip** (the bank slip, the Bit/PayBox confirmation, the cheque photo). Never ask the user which date to use, and never let a different date in the caption or in a message ("today", "yesterday", a date typed by the user) replace it or make you stop and ask. If the two differ, you may mention it in passing; the slip's date stands. **A deposit reported only in words has no slip:** its date is the one the user states; if they gave none, ask for it in one short question - never mention or ask for a photo or a slip.

1. If the deposit came as an image or document (a bank slip, a Bit/PayBox screenshot, a cheque photo), it must have been read with `cap_media_analysis`'s `analyze_media` (load it and read it now if it was not). If it is not one of those (its `doc_type` is not `bank`, `bit`, `paybox` or `check`), stop using this flow and decide what it is from its content.
2. 🚨 **Resolve the client before you reply at all - mandatory, even for a slip sent with no caption or request.** Load `cap_client_read` and call `resolve_client_name` with the client name the user gave for this deposit. If the user gave none, use the payer name `analyze_media` extracted from the slip, **copied verbatim, character for character, letter for letter, exactly as extracted**: never corrected, completed, shortened, or swapped for a similar name or a client from earlier in the conversation. A client resolved for an earlier request does not count for this deposit: resolve it now, even if the name looks exact. Then handle what you found. Report what the slip contains with `cap_send_to_user` (it is sent and you keep going); step 4's offer, if it applies, comes after. Where what you found needs the user's answer (the confirmation question, several candidates, no such client), put it to the user with `cap_send_to_user`:
   - An exact stored name: copy it character for character from the `resolve_client_name` result from here on - in the approval text and in every tool call, never retyped (see `cap_client_read`).
   - A confirmation question (a single close match): use `cap_send_to_user` to put it to the user as-is, and also offer, as its own explicit choice, to create a new client under the exact name the user gave. Proceed with whichever they choose.
   - Several candidates: use `cap_send_to_user` to list each of them by name and ask the user to specify, and also offer, as its own explicit choice, to create a new client under the exact name the user gave. Never pick one yourself.
   - No such client, or the user chose to create a new one: Load `flow_add_client` to create it, then continue with the exact name that was created. If the user declines to add the client, the flow is complete.
3. 🚨 **Record the deposit in the ledger - right now, once.** The money has already landed, so this is a finished event and is recorded as soon as its client is resolved (and the slip's details are read), before anything else is done with it. Load `cap_ledger_query` and `cap_ledger_capture` if not loaded, follow `cap_ledger_capture` exactly (look up the client's ledger history first, then call `report_ledger_recognition` with `verdict` `complete`). If the recording fails, tell the user so. This records only the deposit itself: a Morning document made for it is a separate event, recorded by the document's own flow right after it is created - never record it here.
4. 🚨 **The document: do it if the user asked, offer it if not.**
   - **The user asked** (in the caption or in a message) for a Morning document for this money - an invoice, a combo invoice/receipt, a receipt or a transaction account, or a cancellation of any of these: load `flow_morning_document_write` and follow it through to its end. Do what the user asked; make no offer.
   - **The user said NOT to create a document:** create none and make no offer - the user's explicit instruction always wins.
   - **The user said nothing about a document:** make the offer, but only when the deposit came as an **image** (not text, not a PDF or DOCX) and its client is resolved (an exact stored name; not ambiguous, not declined). Load `cap_approval_with_buttons` now if it is not loaded. Then use `approval_with_yes_no_buttons` to ask, in one short natural Hebrew sentence of your own wording, whether to create a חשבונית מס / קבלה from this deposit. After the offer, send nothing more and wait for the answer. 🚨 The offer carries no amounts, names or dates (the details come later, in the document's own approval). Record with `cap_record_planning_status` that a 320 was offered for this deposit and you are awaiting a yes/no. Do not unload anything yet.
5. The user's next message answers the offer:
   - A yes (a button tap or typed "כן" or similar): load `flow_morning_document_write` and create the חשבונית מס / קבלה (320) from this deposit's details; that flow shows its own approval and creates nothing before it is approved.
   - A no: use `cap_send_to_user` for a very short acknowledgement of your own wording; create nothing.
   - Anything else (the user asked for something different instead): treat the offer as declined, do not ask again, and handle what the user asked normally.
   A bare yes/no outside this offer never triggers it: a short reply always answers the most recent pending question in the same context.
6. End. Use `cap_send_to_user` to report the outcome (skip it if step 5 already said everything). Then unload `cap_media_analysis`, `cap_client_read`, `cap_approval_with_buttons`, `cap_ledger_query`, `cap_ledger_capture` and this flow, keeping any that other work still in progress needs.
