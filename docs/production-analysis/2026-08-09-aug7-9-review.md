## 1. Executive summary

Five documents were created in Morning during the window. **All five are wrong in at least
one material field.** A sixth — a ₪40,000 חשבון עסקה — was approved eight times and never
created at all.

Two independent failure clusters:

- **Cluster A — every document comes out wrong.** Wrong type (305 instead of 320 despite
  proof of payment), wrong payment date (today instead of the extracted transfer date), and
  on the one חשבון עסקה, wrong amount (+18% VAT). The confirmation then reports the amount we
  *asked for*, so none of it surfaces.
- **Cluster B — the approval gate is broken end to end.** The prompt doesn't say what's
  being approved, ends with an ambiguous `לאשר?`, and **rejects the very word it invites**.
  An RTL mark silently turns "כן" into a refusal. A ₪40,000 document failed three times
  because the client lookup rejects the name DeniDin itself printed — and the user was told
  nothing, including one literally empty WhatsApp message.

The through-line: **DeniDin reports intent as outcome.** It said ₪2,360 when Morning stored
₪2,784.80; it re-asked the same question eight times without once saying the previous
attempt had failed. The user is the only error detector in the system, and when she did
catch something ("לאאאאאא"), reflexive agreement talked her out of it.

## 3. P0 — critical

### Cluster A — the documents themselves are wrong

---

#### A1 · Payment received ⇒ must be חשבונית מס קבלה (320), not חשבונית מס (305)

All four Aug 9 invoices were created **from bank-transfer screenshots** — incontrovertible
proof the money had already moved. They were issued as type **305 חשבונית מס**, which Morning
leaves **פתוח / unpaid**.

The user said it outright (session `047cacb7`, turn 7):

> **היית אמור לכל אלו להוציא חשבונית מס קבלה**

DeniDin replied *"נכון, את צודקת — טעיתי בסיווג"* and **took no corrective action** — no
offer to fix, no receipt, no flag.

**Impact.** `get_financial_summary` now reports `שולם: ₪115,074.00 · לא שולם: ₪11,584.80`,
and the entire ₪11,584.80 "unpaid" balance is money already in the bank. Phantom receivables
on the aging report; revenue under-recognised as collected. Recurs on every deposit
screenshot.

**Root cause.** The deposit→document flow calls `create_invoice` (305). The right tool
already exists — `create_combo_document`, type **320 = "חשבונית מס / קבלה"**
(`tools.py:40`, `models.py:38`). It is a selection/guidance gap, not a missing capability.

> ⚠️ **Fixing the type alone is not enough.** `_build_combo_document_payload`
> (`tools.py:261-316`) carries the *same* payment-date bug as the others (A3), so a 320
> issued today would still be dated wrong. A1 + A3 are one payload change and should land
> together; P2-2 (bank/branch/account) touches the same object and can ride along.
>
> *Checked and cleared:* `payment[0].type = 1` (מזומן) is **intended** — all payments are
> booked as cash. Not a defect.

#### A2 · `create_transaction_account` silently adds 18% VAT

User approved ₪2,360. Morning stored ₪2,784.80. User was told ₪2,360.

**Root cause.** `tools.py:174-183` builds the income line with **no `vatRate` and no
`vatType`**, on the bugfix-014 premise that a type-300 "carries NO VAT obligation". Morning
applies its **default ~18%** to any income line omitting `vatRate`.

The codebase already documents this, 600 lines down in the same file (`tools.py:826-831`):

> *"…confirmed live: a 40.0 item with no vatRate became a real 47.2 'amount' owed…"*

Same ×1.18. `_build_create_invoice_payload` (`tools.py:123`) *does* set `"vatRate": 0`,
which is why the four 305s came out correct.

---

#### A3 · The **payment-line date** is "today", never the extracted transfer date — **confirmed**

> Yaron flagged this as "to verify, not sure if this is so". **It is so** — in both the code
> and the ground truth.
>
> **Scope (settled 2026-08-09):** the *document* date being today is **correct** and stays.
> Only the **payment line** must carry the real transaction date, which is already extracted
> from the screenshot and already stored on the ledger event as `txn_date`.

`_build_create_invoice_payload`, `_build_transaction_account_payload`, and
`_build_combo_document_payload` all do:

```python
today = datetime.now(timezone.utc).date().isoformat()
...
"date": today,
"payment": [{"type": 1, "price": amount, "date": today}],
```

None of `create_invoice` / `create_transaction_account` / `create_combo_document` accepts a
transaction or payment date at all (`due_date` is the only date parameter, and it's a
*future* due date).

**Ground-truth confirmation:** all four invoices are dated **09/08/2026**; their deposits
were value-dated **04/08, 05/08→06/08, 06/08, 06/08**. Up to five days out.

**Why it matters.** For a קבלה / חשבונית מס קבלה the payment-line date is the date the money
was actually received — it drives VAT period allocation and bank reconciliation. The value
date is sitting right there in the extracted text of every screenshot
(`תאריך פעולה` / `יום ערך`) and is already captured on the ledger event as `txn_date`.

**Fix.** Thread the extracted transaction date through to `payment[0].date`. Leave
`"date": today` (the document date) exactly as it is.

#### A4 · Confirmations report the requested amount, not the document's real total

`tools.py:249` — `total_amount=response.get("total", amount)`. Morning's `POST /documents`
response carries no usable `total`, so it silently falls back to **the amount we asked for**,
and `format_invoice_confirmation` (`formatters.py:61`) prints that as if authoritative.

This is what let A2 go unnoticed for two days. Structural: any server-side adjustment — VAT,
rounding, currency — is invisible. The confirmation is a restatement of intent wearing the
costume of a receipt.

### Cluster B — the approval gate is broken

---

#### B1 · The prompt invites a word the parser rejects

The confirmation prompt ends `— לאשר?`. The user answers **`לאשר`**. It is **not in the
accepted set**:

```python
_AFFIRMATIVE_REPLIES = {          # ai_handler.py:176
    "yes","yep","yeah","sure","ok","okay","go ahead",
    "כן","אישור","בסדר","אוקיי","אוקי","מאשר","מאשרת","בטח","סבבה",
}
```

`אישור` is there; **`לאשר` is not.** Live consequence (session `12e158e2`, turns 18–26):

```
18 DENIDIN  לעדכן את פרטי הלקוח טלאל קרעאן — לאשר?
19 USER     לאשר                      ← rejected
20 DENIDIN  לעדכן את פרטי הלקוח טלאל קרעאן — לאשר?
21 USER     לאשר                      ← rejected
22 DENIDIN  לעדכן את פרטי הלקוח טלאל קרעאן — לאשר?
23 USER     לא                        ← user gives up
```

The phone-number update never happened. Also rejected in-window: `מאשאת` (typo for מאשרת).

**Yaron's fix is right and is the structural one:** stop asking an open-ended `לאשר?` and ask
a closed question — **`אישור — כן/לא?`** — so the prompt itself teaches an answer the parser
accepts. Widening the whitelist alone would be treating the symptom.

#### B2 · An explicit "כן" is read as a refusal when WhatsApp prefixes an RTL mark

Aug 9 04:00:45 UTC the user sent `‏כן\nלהפיק חשבון עסקה עבור ההסתדרות…`. The log shows
`_call_openai_approval_api: approve=False` — **declined**.

`_is_affirmative_reply` (`ai_handler.py:185`):

```python
normalized = text.strip().casefold()
leading_token = normalized.split()[0].strip(".,!?")
```

`str.strip()` removes whitespace. **U+200F RIGHT-TO-LEFT MARK is not whitespace**
(`'‏'.isspace() is False`), so the leading token is `'‏כן'`, not `'כן'`. Verified:

```
leading token repr: '‏כן'   in whitelist? False
after stripping bidi marks: 'כן'  in whitelist? True
```

8 of the user's messages in this window carry bidi control characters. WhatsApp inserts them
unpredictably for RTL keyboards — so this fires intermittently, which is worse than failing
consistently.

#### B3 · The approval prompt doesn't say what is being approved

22 occurrences in-window of:

```
WARNING  Model produced no narrating text alongside a pending approval … using fallback
         confirmation prompt.
```

The fallback (`ai_handler.py:1333-1350` → `_build_pending_approval_fallback_text`) is
rendered from tool arguments only, so it **drops the description and the user's own
qualifiers**:

```
16 DENIDIN  חשבון העסקה יהיה על סך 40,000 ₪ לפני מע״מ, עבור צו מניעה תומר מרסיאנו,
            ללקוח הסתדרות הכללית החדשה. להפיק ולאשר?      ← complete
17 USER     כן
18 DENIDIN  להפיק חשבון עסקה להסתדרות הכללית החדשה על סך 40000 ₪ — לאשר?
                                                          ← "לפני מע״מ" gone, subject gone
```

For a financial approval gate this is disqualifying on its own: consecutive attempts become
indistinguishable, and the user cannot tell what she is authorising. Directly compounds B4.

#### B4 · The requested document was never created — client lookup fails on the name DeniDin itself printed

Session `047cacb7`, Aug 9 03:56–04:01 UTC. ₪40,000 חשבון עסקה for הסתדרות כללית חדשה.
Three creation attempts, all failed, nothing created.

> **Correction to Yaron's note #2:** the request was a **חשבון עסקה** (type 300), not a
> חשבונית מס קבלה. Different tool, different code path (`create_transaction_account`), and
> it matters — that path also carries the A2 VAT bug, so had it succeeded it would have been
> issued at **₪47,200**.

**Root cause in plain terms.** Morning's client search matches **whole words, from the start
of each word**. Every word you send must match the beginning of a word in the stored client
name. So the query is only as good as its worst word.

The stored client is `הסתדרות כללית חדשה`. Here is what got sent:

| # | Sent as `client_name` | Why it found nothing |
|---|---|---|
| 1 | `הסתדרות הכללית החדשה` | The user's phrasing has a leading **ה** on words 2 and 3. `הכללית` is not the start of `כללית`. Two of three words fail. |
| 2 | `הסתדרות כללית חדשה (ח.פ 589103852)` | The first three words are right, but `(ח.פ` and `589103852)` are also treated as words that must match. No client has them. |
| 3 | `הסתדרות כללית חדשה (ח.פ 589103852)` | Same as #2. |

Meanwhile `list_clients {"name":"הסתדרות כללית חדשה"}` — the **bare** name — returned
**exactly one match, every single time it was tried**. The correct query was available
throughout and was never sent to the create tool.

**Why DeniDin sent the bad string.** `list_clients` prints results as a *display label*:
`הסתדרות כללית חדשה (ח.פ 589103852)` — the company-number suffix is presentation, not part
of the client's name. DeniDin searched, saw one unambiguous result, and reasonably fed that
label back as the client's identity. It behaved correctly; the tool handed it poisoned
output.

> **The one-line version:** the search tool's *output* is not accepted as the create tool's
> *input*. It's like copying "John Smith (age 40)" out of a directory listing and searching
> for it verbatim — the "(age 40)" is now part of the query.

**Why it retried forever instead of stopping.** The tool returns `לא נמצא לקוח בשם הזה.` as
**normal output with `error=None`** — at the protocol level, indistinguishable from success.
`_resolve_pending_approval` (`ai_handler.py:1699`) guards hard against the approved tool
running *more than once* (lines 1754-1776) but has **no guard for it running zero times**,
and no failure counter across turns. So the model just asked again.

**Fix direction.** Either return a stable identifier from `list_clients` that `create_*`
accepts, or strip presentation decoration before searching, or (best) have `create_*` accept
the client_id directly. Plus a consecutive-failure budget so the same action can't be
re-proposed indefinitely.

#### B5 · DeniDin sent no answer at all — repeatedly

Same session. The user approved eight times and, across the sequence, was told **nothing**
about what was happening. Two mechanically distinct failures:

**1 · A literally empty WhatsApp message** (turn 22, 03:58:16).

The "never leave the user with no signal" fallback at `ai_handler.py:1333` is scoped
**inside the `if approval_requests and effective_chat_id:` branch only**. That turn produced
output items `[mcp_list_tools, reasoning, function_call…]` — no `message` item and no
approval request — so:

```
response_text  = ""            # no message item to read
should_reply   = True          # "" != NO_REPLY_SENTINEL   (ai_handler.py:1367)
→ send_response(...)           # whatsapp_handler.py:132 — no empty guard
→ log: "Response sent successfully … 0 chars"
```

An empty bubble was sent and logged as a success. Also happened in session `12e158e2`
turn 16.

**2 · Four replies that said nothing** (turns 24, 26, 28, 30).

The failure `לא נמצא לקוח בשם הזה.` **was surfaced exactly once** (turn 20) and never again.
Each retry emitted a fresh approval request with no narration, so B3's generic fallback
prompt overwrote any explanation. From the user's seat: the same question, forever, with no
error, no progress, and no indication that three documents had already failed to be created.

**Fix direction.** An empty outbound message should be impossible — guard at the point of
send, not only in the approval branch. And a tool failure must be reported to the user every
time it occurs, not only the first time.

## 7. Cross-cutting themes

1. **Reported state ≠ actual state.** A4, A2, B3, P1-2, P2-8 (success logged before the
   failure). Every confirmation that matters should be read back from the authoritative
   system, not restated from intent.
2. **Failures that don't look like failures.** `error=None` on a business failure (B4),
   `WARNING … skipping/rejecting` (P2-5, P2-9, P2-10), empty result for an invalid enum
   (P2-3), an empty message logged as *"sent successfully"* (B5). Nothing escalates;
   everything degrades quietly.
3. **No terminal state on retry.** B4 and P2-8 both retry forever, both cost money per
   attempt, neither has a budget or a dead-letter.
4. **Verification steps that are themselves unverified.** P2-8's "Verify storage" is the
   sharpest case — the check *is* the bug.
5. **Fixes only work in groups.** A1 alone still yields a wrong payment date; B1 alone still
   loses to B2's RTL mark; B4 alone still leaves the user un-told (B5). Sequencing matters
   for estimation.
6. **The user is the only error detector, and she's being talked out of it.**
