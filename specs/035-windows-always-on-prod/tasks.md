# Tasks: Windows Always-On Production Host

**Input**: Design documents from `specs/035-windows-always-on-prod/`
**Prerequisites**: plan.md, spec.md, research.md, quickstart.md, acceptance-tests.md (all present; `data-model.md`/`contracts/` N/A per plan.md)

---

**How this deviates from the generic TDD (Task-a/Task-b) template, and why**:
this feature adds no application code, so there's nothing to write
`tests/unit/test_*.py`-style tests against. The "tests" for this feature —
`acceptance-tests.md` plus the three verification/deploy scripts — were
already written and already reviewed/adjusted by the operator during
`/speckit.clarify` (before any of the configuration work below exists),
which satisfies METHODOLOGY.md §VI's spirit (tests exist and are approved
*before* implementation) without needing new Ta/Tb pairs invented for OS
settings that have no test-writable behavior of their own. Each
configuration task below instead references the specific pre-existing
acceptance-test ID(s) in `acceptance-tests.md` it's verified by.

**Who does what**: almost every task below is a **physical/GUI
configuration step on real hardware** (the Windows laptop) that only the
operator can perform — not something this session can execute directly, no
Windows box being reachable from here. This session's role is: the
already-completed script/doc authoring (Phase 1), and being available to
help interpret `quickstart.md`, troubleshoot a failed verification check,
or adjust a script if a check doesn't work as written against the real
box. Tasks are still written in the standard checklist format for
tracking, but "[ ]" here largely means "operator has completed this step
on the laptop," not "agent wrote this code."

**Tests**: pre-existing (`acceptance-tests.md`), not generated by this
phase — see above.

**Organization**: grouped by user story per spec.md/user-stories.md,
priority order (P1 stories before P2).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Independent of other unfinished tasks in the same phase (order
  between them doesn't matter) — for physical setup this mostly means
  "different setting, no ordering dependency," not "different file."
- **[Story]**: US1–US6 per `user-stories.md`.

## Dependencies & Execution Order

```
Phase 1 (Setup) — includes authoring build_and_package.sh (2026-08-02)
  └─→ Phase 2 (Foundational) — box reachable, Docker Desktop, empty deploy dir + secret config
        └─→ Phase 2a (First deploy, added 2026-08-02) — blocks everything below;
             the box has zero code until this runs once
              ├─→ Phase 3 (US1, P1)  ──┐
              ├─→ Phase 4 (US2, P1)  ──┤ these three can proceed in any order
              ├─→ Phase 5 (US5, P1)  ──┘ once Phase 2a's checkpoint passes,
              │                          though US5/US6 are more naturally
              │                          exercised after US1 is confirmed working
              ├─→ Phase 6 (US6, P1) — a *subsequent* deploy; depends on US1 (needs start/stop working) and benefits from US2 (log reading, to debug a bad deploy)
              ├─→ Phase 7 (US3, P2) — already satisfied by Phase 2/2a; pure verification, no ordering dependency
              ├─→ Phase 8 (US4, P2) — independent of US1/US2/US5/US6, can run anytime after Phase 2a
              └─→ Phase 8b (US7, P2, added 2026-08-02) — independent of every other user story, needs only Phase 2a's deploy directory to exist as an sshfs mount target
  └─→ Phase 9 (Polish) — T040 (cutover) should happen around the same time as first starting prod (Phase 2a); T039/T041 have no strict ordering dependency
```

**Suggested MVP scope**: Phase 1 + Phase 2 + Phase 2a + Phase 3 (US1) — a box that's reachable, has real running containers from a real deploy, and can be started/stopped from the Mac. Everything else (logs, reboot recovery, subsequent deploys, always-on hardening, data-folder mount) layers on top without changing this core.
