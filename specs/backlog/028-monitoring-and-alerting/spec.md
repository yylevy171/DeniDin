# Feature Spec: Monitoring & Alerting

**Feature ID**: 028-monitoring-and-alerting
**Priority**: P1
**Status**: Clarified - Ready for Planning
**Created**: July 30, 2026
**Updated**: July 30, 2026

---

## Problem Statement

`watchdog.py` (one per app, per the 2026-07-21 incident response documented in CLAUDE.md) is this project's only existing runtime health-verification mechanism, and it has two structural gaps, both discovered the same day while investigating an unrelated feature-023 expensive-test failure:

1. **A real, live bug**: `morning-mcp-app`'s watchdog constructs its external tunnel health-check URL as `f"{server_url}/health"`, but `server_url` (per `status_writer.py`) is always the MCP endpoint (`f"{public_url}/mcp"`) — producing `/mcp/health`, a path `BearerTokenMiddleware` does not exempt from auth, so the check always received `401 Unauthorized`. This has been broken since `watchdog.py`'s introduction on 2026-07-21 — the exact day of the incident it was built to prevent a repeat of — and went unnoticed for 9 days because `watchdog.py` had **zero test coverage**.
2. **A structural design gap, independent of (1)**: a health check that is *attempted but fails* (network error, timeout, wrong auth, any transport-level failure) was indistinguishable from "nothing to check yet" (tunnel not started, status file absent) — both produced `None`, and the watchdog's mismatch logic silently no-ops on `None` either way. A persistently-broken check and a benign startup state looked identical, so neither surfaced above a routine `WARNING` log line nobody was watching.

Both are now fixed in `apps/morning-mcp-app/watchdog.py` (2026-07-30): the URL is corrected, and the external/internal checks now report a tri-state (not-attempted / attempted-and-failed / succeeded) so an attempted-and-failed check logs `ERROR`, distinct from the benign no-op case.

**This spec is the follow-up the incident calls for**: watchdog-style health verification currently only runs *reactively*, in a background loop, after the fact, and only within `morning-mcp-app`'s container. Nothing verifies "did this environment actually come up healthy" at the moment a human (or CI) actually starts it — `scripts/run_all.sh` (and the per-app `run_denidin.sh`/`run_morning_mcp.sh` it wraps) currently just runs `docker compose up -d` + `ps` and declares success if Docker itself didn't error, with no verification that the app inside is actually reachable/consistent. And the health-check *logic itself* (what does "healthy" mean, concretely) has, until now, existed as one-off, inline code inside each app's `watchdog.py` — exactly the kind of duplication-risk that let bug (1) above hide for 9 days, since nothing else ever exercised that logic to catch it.

## Clarifications

### Session 2026-07-30
- Q: Should `run_all.sh`'s new sanity check and each app's `watchdog.py` share one implementation, or can they each re-verify health their own way? → A: **Must share the exact same code.** A new helper module per app (`apps/morning-mcp-app/src/denidin_mcp_morning/health_check.py`, `apps/denidin-app/health_check.py`) holds the actual check logic; both `watchdog.py` (the background loop) and a new one-shot CLI mode (what `run_all.sh` invokes right after startup) call into the same functions. No second implementation of "what counts as healthy."
- Q: Is there a way to page/alert a human (or this agent) the instant a check fails, beyond log lines? → A: Not currently — this project has no existing outbound notification channel (no Slack/email/webhook integration) for either app to call into, and `watchdog.py` runs unattended inside a container with no credentials to reach one. Real-time paging is **explicitly out of scope** for this spec; it would require standing up a new notification channel first, which is a separate decision. In scope here: making failures *loud and visible* at the two points a human (or agent) actually looks — container logs (already done for watchdog, 2026-07-30) and `run_all.sh`'s own exit code/output (this spec's main deliverable).
- Q: `denidin-app` has no HTTP server/`/health` route at all (it's a polling WhatsApp bot, not a webhook receiver) — what can its sanity check actually verify? → A: Only what its `watchdog.py` already verifies internally: this container's own declared `environment` (from its config file) is consistent with `shared/active_env.json`. This is a real, meaningful check (it's exactly the 2026-07-21 incident's failure mode) but not a functional liveness probe — denidin-app has no such probe to reuse, and building one (e.g. adding an HTTP server to a bot that currently has none) is out of scope here.
- Q: `apps/denidin-app` and `apps/morning-mcp-app` are always started/stopped together (never independently) — should the monitoring mechanism be one per-app watchdog each, or a single watchdog covering both as one bundle? → A: **One unified watchdog, not one per app** — this is a real architectural change (each app currently bakes its own `watchdog.py` in as its container's PID 1) and needs its own design pass before implementation; captured here as a requirement for this spec, not yet designed.
- Q: (2026-07-30, second incident the same day) An expensive E2E test failed right after `morning-mcp-app-dev` was rebuilt/recreated for the watchdog fix above — root-caused to `requests.exceptions.ConnectionError` / `urllib3.exceptions.NameResolutionError: Failed to resolve 'sandbox.d.greeninvoice.co.il'` inside the freshly-started container, i.e. Docker's internal DNS resolver hadn't stabilized yet when `create_invoice` made its first real outbound call. This is a **previously-documented pattern in this project's own history** (a transient DNS failure immediately after container restart, self-resolving within ~15-30s) — not a code regression, but exactly the kind of thing a startup sanity check should catch instead of a human/CI discovering it via a wasted, billed expensive-test run. → A: Add a DNS-resolution check for the real Morning API host to the startup sanity check (FR6 below).

## Functional Requirements

- **FR1**: Extract `morning-mcp-app`'s existing internal+external health-check logic (`_fetch_health_environment`, `_resolve_status_path`, `_external_tunnel_health_environment` — already fixed 2026-07-30) out of `watchdog.py` into a new, dependency-free (stdlib-only) module, `apps/morning-mcp-app/src/denidin_mcp_morning/health_check.py`. `watchdog.py` imports and calls these functions rather than defining its own copies.
- **FR2**: `health_check.py` (morning-mcp-app) exposes a CLI (`if __name__ == "__main__"`) accepting the status-file path, an optional internal `/health` URL, an expected environment string, and an optional wait/poll window (to absorb the tunnel's known few-seconds startup lag). It prints a clear pass/fail summary per check and exits `0` only if every check that was actually attempted succeeded and reported the expected environment.
- **FR3**: Extract `denidin-app`'s existing environment-consistency check (`_read_own_environment`, `_read_active_environment`, and the inline mismatch comparison) out of `watchdog.py` into a new, dependency-free module, `apps/denidin-app/health_check.py`, with the same "watchdog imports it, doesn't reimplement it" relationship as FR1. Exposes an equivalent one-shot CLI.
- **FR4**: `scripts/run_all.sh`, after starting both services, invokes both apps' health-check CLIs (morning-mcp-app's with a bounded poll/wait for the tunnel to report "running"; denidin-app's directly, no wait needed) and treats the overall start as **failed** — clear error output, non-zero exit — if either check does not pass. This is the actual, literal ask: "if that fails, it's considered the run failed."
- **FR5**: No feature flag — this is new tooling/scripts behavior, not a change to either app's production request-handling code path; nothing here is gated.
- **FR6** (added 2026-07-30, second incident same day): The startup sanity check must also verify DNS resolution to `morning-mcp-app`'s real external dependency host (the Morning/Green Invoice API host from `config.<env>.json`'s `api_url`, e.g. `sandbox.d.greeninvoice.co.il`) succeeds *from inside the running container* — not just that the container is up and its own `/health`/tunnel respond. A container can be "Up" and pass its own internal `/health` while still being unable to reach Morning at all (confirmed live, 2026-07-30: `NameResolutionError` for `sandbox.d.greeninvoice.co.il` immediately after a fresh container recreate, matching a previously-observed transient post-restart DNS pattern in this codebase). Concretely: exec a DNS lookup (or a lightweight real request) against that host inside the `morning-mcp-app-<env>` container as part of the same one-shot sanity check, and fail loud (same as any other check) if it doesn't resolve within a bounded retry window (absorbing the same kind of transient post-restart delay `--wait-seconds` already absorbs for the tunnel).
- **FR7** (added 2026-07-30): This spec covers a **single, unified watchdog** monitoring both `denidin-app-<env>` and `morning-mcp-app-<env>` together as one bundle (matching CLAUDE.md's "ONE ENVIRONMENT SET AT A TIME" — they are never meant to run independently), replacing today's two separate per-container `watchdog.py` processes (one baked into each app's own Docker image as PID 1). Design not yet finalized — open questions include: whether it replaces or supplements the per-container watchdogs, whether it runs continuously in the background (started by `run_all.sh`, stopped by `stop_all.sh`/`killall_containers.sh`) or only as a one-shot startup gate, and how an external, host-level process should be authorized to tear down containers on a real mismatch (today's per-container watchdogs only kill their own local subprocess). Needs its own design/clarification pass before implementation - not to be conflated with FR1-FR4's simpler "shared check code" ask.

## Explicitly Out of Scope

- Real-time alerting/paging to a human or external channel (Slack, email, SMS, PushNotification-style) — no such channel exists in this codebase today; adding one is a separate, future decision.
- Adding an HTTP server/liveness endpoint to `denidin-app` — it has none today and this spec doesn't add one; its check remains the environment-consistency check only.
- Any change to `watchdog.py`'s teardown behavior/policy (still: log and stop the app subprocess, no auto-restart, human must run `killall_containers.sh`) — this spec only changes *where the check logic lives* and *who else can call it*, not what happens on a real mismatch.
- Continuous/periodic monitoring beyond what `watchdog.py` already does every 30s while a container is up — this spec's new CLI mode is a one-shot, run-once-at-startup check, not a new long-running monitor.
